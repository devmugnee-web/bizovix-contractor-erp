# Desktop SQLite implementation status

Updated 2026-09-22. The source implements **Categories, Units of Measurement, Payment Terms and Organizations/Clients**, plus manual verified external backup export. A new backup-export preview installer has been built and verified as described below. This is not a full offline ERP release. The live PostgreSQL application remains the default; `DESKTOP_SYNC_ENABLED` defaults to false. VPS deployment is deferred as requested. Earlier preview artifacts and results remain separately dated.

## Organizations/Clients extension

SQLite migration 3 adds separate organization tables; migration 4 adds cloud query metadata. Earlier migration bytes/checksums, existing command bytes and cursor values remain unchanged. An upgrade first makes and verifies a backup. This domain supports creation and reading only, matching the existing API. Names retain whitespace and case, with the cloud's pinned Unicode length rules for surrogate pairs and presentation selectors. Accepted records cannot be edited through the local draft-recovery route. A rejected create can be revised under the same entity ID with a new immutable operation, retaining its prior history. An existing accepted record, including a hidden one, prevents create revision.

Signed organization read/create capabilities follow the existing authenticated-member scope. The paginated management list additionally requires `masters.read` and `organizationMaster.list`. Members without master-list permission can still reopen their own pending/rejected inline creations after a restart through the local draft list and detail routes. That recovery depends on a signed read capability and a previously initialized profile, independently of accepted-search readiness. If an ACK invalidates the query index and the next pull fails, stored drafts remain readable/revisable offline while accepted queries and new creates wait for cloud ordering to be refreshed. Organization IDs remain unavailable to cloud-only forms until accepted. A duplicate does not silently select or merge another record.

The route adapter preserves the separate typeahead and paginated contracts: trimmed search and 20/100 caps for typeahead, no result for a one-character search, untrimmed search and default eight rows for the paginated HTTP API. The HTTP envelope uses the same outer `meta` and `data` array as Nest. Pending/rejected records are excluded before caps, totals and pagination unless a management screen explicitly asks for them; management drafts appear before the accepted cloud order. The desktop-only hint is stripped before proxying to an older cloud contract.

Real PostgreSQL tests found that Windows sorting and lowercase conversion differ from the PC's JavaScript/ICU rules. Organization snapshots and change pages now carry cloud-derived ordered IDs and a complete scalar lowercase mapping. SQLite stores that query index atomically with the projection and cursor; matching preserves PostgreSQL LIKE wildcards and escaping without evaluating user regex. The supported query-policy server is PostgreSQL 18, UTF-8, libc provider, with default collations on both name columns. Other providers fail explicitly instead of returning guessed results. The cloud caches its complete case map by database/locale identity. An organization ACK or legacy projection without query metadata invalidates the old index; the next sync rebuilds it before local search resumes. This prevents a stale index from silently hiding an accepted record.

The cloud adds organization records to the existing master command/snapshot/change protocol and widens three metadata CHECK constraints in additive migration 74. Existing domain columns and IDs are unchanged. Both ordinary organization creation and implicit organization creation in tender transactions publish to the same stream; reuse of an existing ID does not create a duplicate feed record.

Cloud writers now acquire a shared tenant transaction lock and inspect installed sync metadata before each write. Once a complete metadata family is installed, version/feed capture continues even when public sync endpoints are disabled. This protects subsequent version checks from an intervening web edit. A wholly absent family retains the legacy write path while the feature is off; a partially installed family fails before saving. All participating API instances must run this compatible code; older binaries, direct SQL, and cloud backup rollback still require a controlled reconciliation procedure.

An unavailable command endpoint or authorization denial leaves an uncertain operation pending: neither proves that an earlier delivery failed to commit. A lost acknowledgement followed by pause/restart or authorization recovery therefore replays the original receipt instead of creating a replacement request. Authorization denial still blocks local access until online revalidation. During a temporary cloud outage, a previous valid grant can unlock its saved profile; a fresh profile, expired grant or observed permission withdrawal cannot use that fallback.

The shared HTTP client now binds requests and token refreshes to the session that started them. A late response or logout from account A cannot replay a mutation as account B, replace B's tokens, or clear B's session. Successful web, desktop and development logins clear the previous account's query cache. Logout clears its cache even when an authorization failure has already cleared its tokens. Only a recognized pre-controller authorization denial can trigger one retry. Invoice PDF downloads and company asset previews now use this desktop-aware transport as well.

Existing online document upload limits are preserved: multipart requests spool to a private temporary file with an aggregate 216 MiB cap covering the current maximum 20 × 10 MiB batch; the cloud still validates each file. Large uploads use a file-backed stream rather than a large in-memory buffer. Only an explicit pre-controller JWT denial permits one authenticated retry; network failure does not replay business requests. Receipt/bill print windows and same-origin document previews are retained without exposing the main application's bridge.

Category selectors for foreign-key-based cloud workflows use only accepted cloud records. Document Purchase's existing Work Category field stores a free-text name rather than a category ID, so that selector explicitly retains local names and its inline Add Category flow. This distinction preserves the existing backend field contract.

UOM and Payment Term management opt into local drafts; their default shared hooks expose only accepted IDs/values to online ERP forms. Existing UOM codes remain immutable. Review forms allow correcting a rejected new code and explicitly clearing optional symbol/description text. New offline commands reject whitespace-only required names/codes before enqueue; legacy blank cloud values remain readable and the original web mutation contract is retained.

Customers do **not** need to download SQLite, PostgreSQL, Node or pnpm. Initial activation needs the configured cloud service and the customer's account. Vendor/developer build configuration is separate from customer installation.

The grant lifetime defaults to 24 hours and can be configured on the server up to 168 hours. While online, sync renews a matching grant before expiry. Explicit authorization denial prevents cached offline access until a successful online sign-in. Pending data is retained. After a cloud password change, desktop login asks for the previous local password, verifies the current password online, makes a verified backup, and rekeys the vault without changing local command IDs. Recovery without the previous password and a complete customer restore/switch UI remain unimplemented.

Only the credential/grant vault is encrypted by this pilot. SQLite records are ordinary local files protected by the OS user directory; full database encryption and key recovery have not been delivered.

## Data preservation

- No pre-existing application or customer database was reset, seeded, migrated, converted or overwritten. No customer rows were updated or exported; no uploaded documents were moved. The newly created test database received the reviewed additive bank-charge migration and isolated fixture resets described below.
- Earlier checks read PostgreSQL catalog/schema definitions in a read-only session and created fresh `bizovix_test_desktop_*` databases. The current helper builds new `bizovix_test_bootstrap_*` databases directly from the reviewed source baseline without reading the application's schema. Existing business tests may reset their own fixtures only inside that exact newly generated database; both the URL and live database identity are checked. Test databases are retained for inspection, never automatically deleted.
- Local writes and their immutable outbox commands commit together. A lost acknowledgement replays the same operation identity; it does not create a new business request.
- Rejected edits remain visible. Revisions create new commands; prior command history remains stored. Accepted cloud data is separate from local drafts.
- SQLite opening fails on an unknown, corrupt or newer schema instead of recreating the file. Automatic daily and manual profile backups verify integrity, profile, schema and file hashes; existing backup files are never overwritten or automatically deleted. Manual export creates a new verified external bundle through a native chooser and refuses the active data tree or an existing destination. Recovery refuses an existing destination and preserves the active database. A customer restore/switch UI, attachment recovery and full-data reconciliation remain pending.
- Cloud signing private keys, database URLs and JWT signing secrets are excluded from the desktop child process environment and installer configuration.

## Run the developer checks

Use Node 24.13 or newer for local storage tests. Customers use the bundled Electron runtime.

```powershell
pnpm test:desktop
node scripts/test-desktop-cloud.mjs
node scripts/test-desktop-cloud.mjs --all-integration
```

The cloud test helper accepts only a local PostgreSQL host, creates a new database and never migrates the configured application database. It now defaults to a source-derived [fresh cloud baseline](cloud-database-bootstrap.md), retaining SQL-only constraints and indexes. Two historical migrations contain captured non-SQL CLI warnings; their original files remain unchanged. The explicit `--schema-snapshot` compatibility option remains available, but the default no longer depends on the developer application's schema. PostgreSQL 18 and the pinned Prisma version are required by this baseline.

Build shared packages in order (`@bizovix/types`, then `@bizovix/validation`, then `@bizovix/api-client`), then API, renderer and Electron. Electron package preflight expects a completed Next standalone build. Electron scripts include `probe:runtime`, `probe:renderer`, `probe:local-service` and package input validation.

Cloud pilot settings are documented in [the cloud module](../../apps/api/src/modules/desktop-sync/README.md). `apps/desktop/electron/desktop-config.json` is deliberately empty until the vendor supplies the VPS API URL, matching public verification key and issuer. It contains no private key. An unconfigured preview can start, but cannot activate an account. Do not distribute it as a usable customer release.

Every cloud writer must run the compatible transaction/capture code described above. Public sync can be disabled without disabling installed capture. A database restore, older writer, or manual SQL bypass can still leave stale versions and missing events; the module does not repair that state automatically. Such recovery must first block acceptance and reconcile versions, pending commands and receipts. Rotating only the cursor epoch is insufficient because current commands do not carry an epoch. No devices have been activated against the unchanged application database by this work.

## Work still required for the requested full product

1. Port all remaining ERP workflows to local repositories using their existing validation, exact amounts, transactions, numbering and authorization rules. Categories, Units, Payment Terms and Organizations/Clients are the implemented nonfinancial master workflows. Parties, items, accounting, tenders, procurement, inventory, payroll, LC, project workflows and reports still use cloud services. Party summary/detail also depends on payables/documents and cannot be represented honestly by a party-only cache.
2. Add per-domain sync commands and consistent feeds for every mutation, including attachments, reversals and deletes. Never replay arbitrary financial HTTP requests as an offline queue.
3. Prove full business parity and ledger/stock reconciliation, including two-PC edits, interrupted writes, retries and permission changes. The earlier unit/lint failures and new-database bootstrap are addressed; they do not establish offline parity for remaining financial workflows.
4. Complete recovery when the previous password is unavailable, licensing/device-management UX, safe cloud-restore epoch reconciliation, automatic cloud/attachment backup and customer restore/switch UX. Previous-password rekey, online grant renewal, daily verified local backups, manual verified external export and recovery into a separate directory are implemented. A signed permission grant is not a complete SaaS licensing system.
5. Rehearse legacy-data migration into a fresh destination after verified database/document backups. Compare counts, exact amounts and business totals before changing any customer's active data source.
6. Validate fresh installation, upgrade, uninstall/reinstall with retained data, low-disk and power-failure behavior, performance and supported Windows versions. Sign the final installer, configure the VPS and verify authenticated mobile access.

Before parties/items follow, preserve `Party.roles` as a multi-value enum list, party payable/document aggregates and separate contact deletion paths. Item creation depends on accepted category/UOM/vendor IDs and exact rates. `NumberingService.next` now initializes and increments defaults through the caller's transaction; concurrent first allocation uses `createMany(..., skipDuplicates: true)`. Rollback, same-transaction allocation, concurrent initialization, tenant isolation and year rollover pass against a new isolated PostgreSQL database. Final business numbers must still remain cloud-authoritative or use an explicitly reserved range; independent offline PCs cannot safely invent the same final number. Parties/items are not completed local workflows.

These are release requirements, not claims of completed work. See the remaining architecture documents for file-level migration design.
