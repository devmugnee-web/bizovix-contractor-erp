# Desktop local service

This service runs under Electron's bundled Node runtime. It stores Categories, Units of Measurement and Payment Terms in SQLite and proxies other ERP requests to the real cloud API. It does not implement offline financial modules.

`src/main.mjs` is the owned-process entry point. The Electron supervisor supplies a private data root, a fresh request capability, a fresh instance ID and vendor cloud public configuration. Readiness is a JSON message on stdout; origin approval and shutdown arrive over stdin. The listener binds only to `127.0.0.1` on an OS-assigned port. Every HTTP request requires `X-Bizovix-Local-Capability`; browser origins must match the approved renderer origin.

Initial login authenticates with the cloud and obtains a device-bound Ed25519 grant. The cloud tokens and grant are stored in a password-derived AES-GCM vault; the renderer receives only random local session tokens. Later offline login verifies the vault and grant. Explicit cloud denial blocks cached offline use until successful online login, while preserving stored work. Sync renews unexpired grants near expiry; an already-expired grant requires online sign-in. The previous-password recovery flow verifies the current cloud password and backs up the profile before rekeying. Forgotten-password recovery and SaaS license policy remain incomplete.

Local routes under `/api/v1` are `auth/login`, `auth/refresh`, `auth/me`, `auth/logout`, `master-categories`, `master-categories/:id`, `uoms`, `uoms/:id`, `payment-terms`, `payment-terms/:id`, `desktop/status`, `desktop/sync` and `desktop/backup`. UOM/Payment Term reads and writes require the matching signed capability and an initialized local snapshot. Older category-only grants retain their existing cloud route behavior. The two added domains have separate cloud feeds and local cursors; they never consume category v1 sequence numbers. A renewed grant can enable and bootstrap a new domain during sync.

Desktop dev-login is disabled. Supported mutations save an immutable command atomically with the local draft. Sync sends the same operation ID until acknowledged; conflicts retain both draft and current cloud values. Unsupported offline mutations fail visibly and are never put into an unsafe generic replay queue. Status reports only permitted, initialized offline modules.

`backups.mjs` creates daily verified SQLite/vault bundles, supports manual backup, and restores only to a fresh directory. It never overwrites an active profile. Existing backup candidates are fully verified after restart, including rejection of nonempty WAL/journal sidecars. Logout drains pending backups before closing storage. See [backup and account recovery](../../../docs/offline-first/backup-and-account-recovery.md) for support commands and remaining restore/external-backup limitations.

Start through the Electron supervisor. Customers do not configure this process or install SQLite separately. For isolated development/testing the entry point reads `BIZOVIX_LOCAL_DATA_ROOT`, `BIZOVIX_LOCAL_CAPABILITY`, `BIZOVIX_LOCAL_INSTANCE_ID`, `BIZOVIX_CLOUD_API_URL`, `BIZOVIX_CLOUD_PUBLIC_KEY`, `BIZOVIX_CLOUD_ISSUER` and `PORT`. HTTP cloud endpoints are forbidden except explicit loopback development with `BIZOVIX_ALLOW_INSECURE_LOCAL_CLOUD=true`.

Multipart requests have a bounded 216 MiB aggregate ceiling, covering the API's largest current batch (20 BOQ PDFs at 10 MiB each) plus form fields/framing. JSON and other bodies retain a 16 MiB ceiling. Multipart bytes are spooled to a unique private temporary file and forwarded with a [file-backed Node 24 Blob](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsopenasblobpath-options), then cleaned up when the request finishes; cloud file/count/type limits remain authoritative. Temporary files are not queued offline. An interrupted process can leave a temporary file for OS cleanup. Upload receipt and cloud upload timeout are each bounded at 120 seconds. Only an explicit pre-controller JWT denial permits one retry of the same immutable upload; network errors are never replayed.

See [implementation status](../../../docs/offline-first/implementation-status.md) and the tests in `test/local-service.test.mjs`. Never point test fixtures or cleanup at a customer's application data directory.
