# Desktop master sync

This module implements **Master Categories, Units of Measurement, Payment Terms and create-only Organizations / Clients**. It does not enable offline accounting, replicate arbitrary database rows, or migrate existing ERP data. The normal PostgreSQL application remains the default.

Enable the current module only after the additive `20260921120000_add_desktop_category_sync_pilot`, `20260921150000_add_desktop_master_sync` and `20260921160000_add_desktop_organization_master_sync` migrations have been verified/applied to the intended cloud database:

```text
DESKTOP_SYNC_ENABLED=true
DESKTOP_SYNC_ISSUER=https://your-configured-cloud-api.example
DESKTOP_SYNC_PRIVATE_KEY_PEM=<Ed25519 PKCS8 private key, server only>
DESKTOP_SYNC_OFFLINE_HOURS=24
```

The private key must never enter the desktop installer. The desktop pins the matching public key and exact issuer. Registration fails closed if signing configuration is absent/invalid. Maximum configured grant lifetime is 168 hours; default is 24. A grant carries the authenticated user's permitted master capabilities and does not grant administrator access, arbitrary modules, or independent paid-license entitlement. Existing subscription/device policy integration remains a separate release requirement.

`DesktopSyncModule` must be imported into the API application module. Global JWT and permission guards remain active. All routes are under `/api/v1/desktop-sync` and retain the application's `{success,data}` response envelope:

- `POST register`: `{deviceId,deviceName?}`; returns identity and `{grant:{payload,signature}}`. Device IDs are UUIDs and permanently bound to one organization/user unless a separately authorized device-management workflow changes that state.
- `POST commands`: one `{operationId,deviceId,schemaVersion:1,commandType,entityId,expectedVersion,payload}`. Command type is `masterCategory.create` or `masterCategory.update`; payload uses the existing category DTO. Create expects null/omitted version; update expects a positive integer. Returns `{operationId,category,cursor,replayed}`.
- `GET snapshot?deviceId=...`: returns `{categories,cursor,epoch,schemaVersion:1}` from a repeatable-read transaction.
- `GET changes?deviceId=...&cursor=...`: returns `{changes:[{kind:'upsert',category,operationId,cursor}],cursor,hasMore}`. Page size is 200.

Category wire shape is `{id,type,name,description,isActive,version,createdAt,updatedAt}`. Both timestamps are ISO strings from the existing authoritative category record. Grant signature is Ed25519 over UTF-8 JSON with object keys sorted recursively and array order preserved; signature bytes use base64url. Payload contains `formatVersion`, `issuer`, `audience:'bizovix-desktop'`, device/user/organization identifiers, an `AuthUser` snapshot, permissions, allowed capabilities and ISO issued/expiry times.

Additional masters use separate routes and never advance the original category clock:

- `POST masters/commands`: `{operationId,deviceId,schemaVersion:1,entityType,commandType,entityId,expectedVersion,payload}`. `entityType` is `uom`, `paymentTerm` or `organizationMaster`; UOM and terms accept matching `.create` / `.update`, while organizations accept only `organizationMaster.create`. The original master DTO validates the nested payload. Returns `{operationId,entityType,record,cursor,replayed}`.
- `GET masters/snapshot?deviceId=...&entityType=...`: `{records,cursor,epoch,schemaVersion:1,entityType}` from a consistent repeatable-read snapshot.
- `GET masters/changes?deviceId=...&entityType=...&cursor=...`: `{changes:[{kind:'upsert',record,operationId,cursor}],cursor,hasMore,entityType}`, with the same 200-event page limit and gap checks.

Organization snapshot and change responses additionally include `queryIndex:{formatVersion:1,orderedIds,caseMappings}`. `orderedIds` contains the tenant's current full catalog in the same PostgreSQL `shortName ASC` order used by the existing web endpoints; a paged feed can include IDs not reached by that page yet. `caseMappings` lists every Unicode scalar changed by this database's `lower()` operation. The desktop persists this index atomically with accepted records/cursors and uses it for filtering before typeahead caps or pagination. It does not substitute Node's locale sorting or Unicode lowercasing, which can differ from the cloud. Pending creations are a separate management overlay and never enter accepted business pickers.

This search protocol currently supports PostgreSQL 18 with the **libc locale provider, UTF-8 encoding and default collation on both organization name columns**. Other providers/column collations fail closed with 503 until their semantics are implemented. The helper checks the database/column policy on every pull. It computes the complete scalar map once per service instance and database/locale/version identity, excluding NUL and surrogates; failed computations are retried rather than cached forever. The context-free behavior follows PostgreSQL's [libc lower implementation](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/pg_locale_libc.c) and [multibyte ILIKE implementation](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/like.c). The full order/map per pull is intended for the existing small master catalog; larger-catalog protocol optimization remains release work.

UOM records contain `{id,code,name,symbol,isActive,version,createdAt,updatedAt}`; payment terms contain `{id,name,days,description,isActive,version,createdAt,updatedAt}`; organizations contain `{id,shortName,fullName,version,createdAt,updatedAt}`. Organization names retain their exact case and whitespace and existing case-sensitive short-name uniqueness. A conflicting create is rejected without merging identities. Tenant IDs are derived from authenticated identity, never accepted from payloads or copied into projections. Each entity type has an independent tenant clock/epoch, immutable feed and version metadata. Existing records start at version 1 without rewriting their data. The original receipt key remains global across all commands, preventing reuse of an operation ID with a different entity or payload.

Read capabilities `uom.read` and `paymentTerm.read` require `masters.read`; UOM create/update also require `uom.manage`, and payment-term create/update also require `payment_terms.manage`. Active authenticated members receive `organizationMaster.read` / `.create`, preserving the existing JWT-only typeahead/create contract. Only members with `masters.read` receive `organizationMaster.list`, required for the paginated management list. All cloud commands still recheck current membership and device ownership. The signed grant remains format 1 with additive capability strings. Old clients continue using the unmodified category routes, hashes, tables and cursors; new clients must not queue master commands when their grant lacks the corresponding capability. Existing v1 grants remain valid for their original capabilities.

Normal web master writers share transaction helpers with desktop commands: once the corresponding metadata is installed, domain mutation, audit (where the existing domain has one) and stream event commit together even while external sync endpoints are paused. Tender creation/update that implicitly creates an organization uses the same organization stream lock and caller transaction; selecting an existing organization produces no new event. Desktop commands add their version check and receipt in that same transaction. UOM code remains immutable on update; omitted optional text retains its existing value, while explicit null clears it. New offline UOM/term commands reject whitespace-only names/codes before mutation; organization commands retain their original DTO rules. Previously stored records remain unchanged. Deactivation uses the existing `isActive` field and an upsert event; there is no new destructive delete command.

Cloud command acceptance rechecks database membership/permissions and registered-device scope. Local grants are never accepted as cloud bearer credentials. Duplicate operation identity requires the same actor and canonical payload hash. Domain write, audit, version metadata, immutable feed projection and result receipt commit together. Financial services are never called by this pilot.

Version state uses a separate new table; existing `MasterCategory` columns and IDs remain unchanged. Pre-pilot categories begin at version 1. Normal REST category writes join the same clock lock and feed as desktop writes once metadata is installed. There is no category-delete operation and no feed or receipt pruning in this pilot. Wrong epoch, ahead cursor or a missing change produces HTTP 409 with a `RESNAPSHOT_REQUIRED` message prefix. The client must preserve pending commands while replacing its accepted snapshot.

Operational requirements:

1. Deploy compatible capture code to every API instance that writes these masters. `DESKTOP_SYNC_ENABLED=false` pauses external sync routes with retryable HTTP 503; it does not stop change capture once metadata is installed. Each normal writer checks the catalog inside its transaction under the same tenant advisory lock used by enrollment, without caching absence. This prevents another compatible instance's enrollment from racing an untracked writer. Older binaries, direct SQL writers and database restores still require a controlled maintenance procedure: block command acceptance, reconcile domain versions, pending commands and receipts, then review epoch rotation/resnapshot. Epoch rotation alone is insufficient because commands carry an expected version but no epoch. Automated restore administration is not implemented here.
2. Never prune receipts while devices may replay those operations. Never restore an old cloud database and accept pending retries without reconciliation.
3. Existing legacy REST updates do not carry expected versions; their existing behavior is preserved. They serialize and increment the shared version, so a stale desktop update is rejected. Conflict protection for concurrent legacy REST users is outside this pilot.
4. Each snapshot loads its small master catalog in one response. Pagination/materialized snapshots, explicit device revocation UI, production license enforcement and full-module authorization invalidation are subsequent release work. The local service renews signed grants while online.
5. A wholly absent metadata family and disabled endpoint flag retain ordinary domain writes after a catalog check; no missing sync table is queried. Partial metadata fails closed, and organization writes require the reviewed three-CHECK upgrade whenever master metadata is installed. Missing or malformed installed metadata cannot silently disable capture. Cloud tables are never created on application startup.

Validation uses category/master/capture unit tests and real-service desktop integration suites, including organization authorization, exact-name conflicts, indirect tender creation rollback and paused capture. `desktop-roundtrip.integration-spec.ts` boots the real Nest API with JWT authentication and separate local-service processes, including PostgreSQL/SQLite organization query comparison, reviewed rejected creation, two-PC master conflicts, a lost acknowledgement and offline restart persistence. These suites require the fail-closed `TEST_DATABASE_URL` setup, add uniquely identified fixtures, and do not reset the database. The owning runner must provide an isolated database; the safe runner retains it for inspection. No test or startup path runs migrations against the user's current `DATABASE_URL`.
